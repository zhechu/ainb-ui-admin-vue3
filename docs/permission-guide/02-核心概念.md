# 02 · 核心概念

看懂这一章，配置时就不用猜了。

---

## 一条授权 = 主体 × 资源 × 动作 × 效果

这是整套体系的最小单元，存在 `sys_grant` 表里。除这四项外还可以叠加
**行过滤规则**、**字段显示模式**、**有效期**、**上下文限定**。

---

## 主体：授给谁

| 类型 | 含义 | 怎么定位 | 能不能配 |
|---|---|---|---|
| `ROLE` | 角色 | 角色 id | ✅ 常用 |
| `USER` | 具体某个人 | 用户 id | ✅ |
| `DEPT` | 部门 | 部门 id | ✅ |
| `POST` | 岗位 | 岗位 id | ✅ |
| `GROUP` | 用户组 | 主体 id | ⚠️ **暂不可用**，见下 |
| `ALL` | 所有登录用户 | 编码 `all-users` | ✅ |
| `SYSTEM` | 系统身份（非人） | 编码，如 `bpm-engine` | ✅ 仅特殊场景 |

> ⚠️ **`GROUP` 用户组目前没有管理入口，不要用。**
>
> 判定引擎支持它（主体闭包会算、授权表也存得下），但**没有建组和管理成员的界面**：
> 后端只有一个给下拉框用的只读查询接口，前端没有对应页面。
> 用户组也没有独立业务表，成员关系要直接写 `sys_subject_member`。
>
> 现状是全库 `GROUP` 主体 0 个、用它的授权 0 条。
> 另有一套 `bpm_user_group`（BPM 用户组，同样 0 行）尚未与它合并。
>
> **需要「一组人共享一套权限」时，用角色代替**——角色还支持继承，表达力更强。

**一个人身上会同时命中多个主体**：他本人、他的每个角色、他的部门、他的岗位、
以及 `ALL`。这一整套叫**主体闭包**。（用户组也在闭包的计算范围内，但目前没有数据。）

角色还支持**继承**——子角色自动拥有父角色的授权，继承链也在闭包里。

> `ALL:all-users` 的典型用途是把「不限制」表达成一条显式授权。
> 比如流程发起范围留空表示「谁都能发」，系统会投影成一条 `ALL` 授权，
> 而不是靠「没配就放行」。

> `SYSTEM` 主体给引擎自己用。比如子流程被父流程调起时，
> 发起人不是某个自然人而是流程引擎，判定用的主体就是 `SYSTEM:bpm-engine`。

## 资源：授权对什么

资源是一棵树，存在 `sys_resource`。

| 类型 | 是什么 | 默认效果 |
|---|---|---|
| `MENU` | 目录、菜单（树的结构节点） | — |
| `ACTION` | 权限点，对应一个按钮或接口 | **拒绝** |
| `DATASET` | 一张表单 / 一张原生表 | 放行 |
| `COLUMN` | 列表里的一列 | **放行** |
| `FIELD` | 详情里的一个字段 | **放行** |
| `PROCESS` | 一个流程 | **拒绝** |
| `CATEGORY` | 流程分类 | 拒绝 |

### 默认效果为什么不统一

这是刻意的，反过来会出大问题：

- **按钮/流程默认拒绝** —— 没授权就不能用，这是权限系统该有的样子
- **列和字段默认放行** —— 绝大多数字段本来就不该逐个配权限。
  如果默认拒绝，一张表单会「所有字段全部消失」

### 继承

授权沿资源树**从祖先往后代**继承。给「客户管理」这个节点配了 VIEW，
它下面的所有列和字段都继承这条。

所以常见配法是：**在数据集上配一条放行，只对个别敏感字段单独配收紧。**

---

## 动作：能做什么

| 动作 | 用在哪 |
|---|---|
| `VIEW` | 通用查看。按钮层的「能不能点」也是它 |
| `CREATE` / `UPDATE` / `DELETE` | 增删改 |
| `EXPORT` | 导出 |
| `IMPORT` | 导入 |
| `PRINT` | 打印 |
| `REFERENCE` | 被别的表单的关联控件引用 |
| `START` | 发起流程 |
| `DESIGN` | 改流程设计 |
| `MANAGE` | 流程管理员 |
| `VIEW_ALL` | 看某流程的全部实例 |
| `*` | 全部动作 |

**动作必须分开配。** 一条授权只覆盖一个动作（或 `*`）。
「能查但不能删」就是配 `VIEW` 不配 `DELETE`。

---

## 效果与优先级

只有两个值：`ALLOW` / `DENY`。判定顺序：

```
1. 收集这个人的全部主体
2. 沿资源链（自身 + 所有祖先）收集所有命中的授权
3. 有任何一条生效的 DENY  →  拒绝          ← DENY 永远赢
4. 有任何一条生效的 ALLOW →  放行
5. 一条都没命中           →  看资源自己的 default_effect
```

**第 5 步是最容易误解的地方**：「没配过」不等于「拒绝」，而是回落到资源的默认效果。
所以菜单没配 = 拒绝，字段没配 = 放行。

### DENY 的用法

DENY 用来在大范围放行里挖洞。比如：给全体员工放行客户表单，
但对「实习生」这个角色配一条 DENY —— 实习生即使同时属于其它有权限的角色，也进不去。

> ⚠️ DENY 也会被继承。给一个流程分类配 DENY，它下面所有流程都被拒。
> 只想拦一个流程就配在那个流程上。

## 行过滤规则：他能看到哪些行

授权决定「能不能进这张表」，行过滤规则决定「进来后能看到哪几行」。

规则挂在授权行上（一条授权可以挂一条规则）。规则本身在【规则管理】里维护，可复用。

### 规则靠槽位工作

规则说的是「只看 `owner` 是自己的行」，而 `owner` 到底对应哪一列，
由**槽位映射**告诉它：

```
规则：{owner} = 当前用户
                 ↓  槽位映射
数据集「客户」： owner → create_user_id
                 ↓
最终 SQL：  WHERE create_user_id = 当前用户id
```

**槽位没配 = 规则求不出条件 = 一行都看不到**（不是「不过滤」）。
这是设计上的选择：求不出来时宁可全拒，也不能悄悄放开。
出现这种情况后台会打 ERROR 日志，明确写「求不出条件，按不授予任何行处理」。

四个标准槽位：

| 槽位 | 含义 | 典型列 |
|---|---|---|
| `owner` | 归属人 | `create_user_id` |
| `dept` | 归属部门 | `dept_id` |
| `status` | 状态 | `status` |
| `bizKey` | 业务主键（流程/共享类规则要用） | `id` |

### 没配规则 = 不过滤

授权上不挂规则，就是「这张表的行全都能看」。这是安全的默认值——
标记一张表支持行过滤，不会改变任何现有行为，直到有人真的配了规则。

## 字段显示模式

三个值，**必须是这三个，不能写别的**：

| 值 | 含义 |
|---|---|
| `EDITABLE` | 能看能改 |
| `READONLY` | 能看，提交的值被丢弃 |
| `HIDDEN` | 看不到，提交的值被丢弃 |

多条授权同时命中时取**最严格**的那个（HIDDEN < READONLY < EDITABLE）。

字段权限在四个出口都生效：**列表、详情、导出、导入**。
写路径（新增/修改/导入）会把 READONLY 和 HIDDEN 的字段值直接丢掉——
因为界面上的禁用不是安全边界，抓包重放照样能提交。

---

## 有效期

授权可以设到期时间。到期后那条授权失效。

**对 ALLOW 和 DENY 一视同仁**：

- 到期的 ALLOW = 权限自动回收
- 到期的 DENY = **临时封禁自动解封**

第二条是刻意这样设计的。想要「永久禁止」就不要设到期时间。

---

## 上下文限定（进阶）

授权可以限定「只在某个上下文里生效」，目前用在流程节点上：
「这个字段只在审批节点 A 可编辑，别的地方只读」。

⚠️ 上下文限定的授权**与当前上下文无关时完全不参与判定**——
不会因为它存在就跳过默认效果的回落。配错的表现曾经是
「给某节点配了一条 ALLOW，该字段在其它所有地方反而不可见」，这是个已修的缺陷。

---

## 和旧的「角色-菜单」有什么关系

旧模型是 `system_role_menu`（角色勾菜单）。新引擎**不看它**。

角色管理里那个「菜单权限」按钮属于旧模型，配了对新引擎无效。
**统一用「资源授权」。**

前端的菜单树和按钮显隐，现在也都来自新引擎的判定结果，与后端鉴权同源。
