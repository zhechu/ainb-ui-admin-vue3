# 05 · 排错手册

这套系统的故障形态几乎都是**静默的**：配了、保存成功了、没有任何报错，但不生效。
所以排错不能靠「看有没有报错」，得靠工具定位。

---

## 第一步：永远先用权限诊断页

**入口**：【系统管理 → 权限诊断】

填三项：

| 项 | 填什么 |
|---|---|
| 权限标识 | 要查的权限串，如 `system:user:query` |
| 动作 | 默认 VIEW，流程相关要选对应动作 |
| 用户 id | **填那个有问题的人的 id**。不填是查当前登录用户 |

它会把判定路径完整展开：

### 1. 主体闭包（subjects）

这个人命中的全部主体。**先看这里** —— 如果你以为他有某个角色但列表里没有，
问题就在角色没生效，而不在授权。

常见原因：直接改库表加角色，没清 `user_role_ids:<用户id>` 缓存。

### 2. 资源链（resourceChain）

这个权限串对应的资源，以及它的祖先链（从最具体到根）。

- **链是空的** → 资源表里没有这个权限串。配了授权也没用，因为没有对象。
  一般是权限点没入库，或者权限串拼错了。
- **链里有你没想到的祖先** → 祖先上的 DENY 会继承下来，往上逐个查

### 3. 全部授权行（allGrants）

资源链上的**所有**授权，每行都标注了三件事：

| 标注 | 含义 |
|---|---|
| 命中主体 | 这条授权的主体在他的闭包里 |
| 命中动作 | 这条授权的动作覆盖你查的动作 |
| 参与决策 | 同时命中主体和动作、且没过期 —— 只有这种才真的算 |

**看「参与决策」那一列。** 你以为配好的那条如果没参与决策，
对照前两个标注就知道是主体不对还是动作不对。

### 4. 结论与原因

- `ALLOWED` / `DENIED`
- 原因写明是「命中了某条 DENY」、「命中了某条 ALLOW」，还是「没命中任何授权，
  回落到资源的 default_effect」

### ⚠️ 诊断页对超管不短路

后端鉴权对超管直接放行，但诊断页**故意不短路** —— 它展示的是授权引擎真实的判定路径。

所以用超管查，经常显示 `DENIED`（因为确实没给超管配那条授权），
**这不代表超管用不了**。查超管没有意义，要查那个真正有问题的账号。

## 按症状查

### 症状：菜单不出来

1. 诊断页查这个菜单对应的权限串，看结论
2. 结论是 ALLOWED 但菜单还是不出来 → 检查菜单本身是否被停用、是否 `visible=false`
3. 结论是 DENIED → 按诊断结果里的原因处理

> 菜单树和按钮显隐来自同一套判定，不会出现「按钮有了但进不去页面」这种分叉。

### 症状：按钮不显示

同上。按钮的权限串一般是 `模块:功能:动作` 形式。

### 症状：按钮显示了，点下去报「无权限」

这是**前后端判定不一致**，说明某处配置让两边读到了不同的东西。

已知原因：同一个权限串对应了**多行资源**（同一权限挂在多个菜单上），
而授权配在了其中一行上。这个缺陷已修复——如果仍然出现，请反馈。

### 症状：列表一行都看不到

**先怀疑槽位。** 行过滤规则求不出条件时，行为是「一行都不给」，不是「不过滤」。

1. 打开该数据集的资源配置 → 槽位映射，确认规则依赖的槽位有映射
   （仅自己的数据要 `owner`，本部门要 `dept`，流程参与者/共享类要 `bizKey`）
2. 检查规则的参数是否填了（「指定状态可见」和「指定字段等于」必须填参数）
3. 请开发查后台日志，会有明确的一行：
   `[resolve][ALLOW 规则 N（授权 M）求不出条件，该条按「不授予任何行」处理`

### 症状：配了字段隐藏但还能看到

1. 确认字段模式的值是 `HIDDEN`，不是别的写法
2. 确认配的是对的那个资源 —— **列（`:col:`）和字段（`:fld:`）是分开的**，
   列表里要隐就配 `:col:`，详情里要隐就配 `:fld:`
3. 确认这个人没有同时命中一条更宽松的授权 —— 多条命中时取最严格，
   但如果他压根没命中任何字段授权，就回落到默认放行

### 症状：配了字段隐藏，结果所有人都看不到了

字段模式取**最严格**。如果给「全体员工」配了 HIDDEN，
那么同时属于全体员工的经理也会被压住。

正确做法：不给大范围配 HIDDEN，只给**需要被限制**的那个角色配。

### 症状：流程谁都发不了

如果是从别的环境导入流程定义、或直接改过库里的发起范围字段 ——
发起范围的投影只在部署时跑。重新部署一次那个流程即可。

### 症状：单子昨天能打开今天打不开

参与记录可能缺失（历史流程没有自动登记）。请开发跑一次参与人补登记脚本。

### 症状：取消共享后对方还能看到

这是**预期行为**，不是故障。取消共享只删那条共享记录；
对方通过创建人/本部门/角色授权等别的途径本来就看得见的话，照样看得见。

要真正挡住，在授权列表里加一条针对他的 DENY。

## 什么时候该找开发

以下情况不是配置能解决的：

| 现象 | 说明 |
|---|---|
| 资源链是空的，且权限串确认没写错 | 权限点没入库，需要执行 SQL 并重启 |
| 字段权限页签里什么都没有 | 该表的列/字段资源没登记 |
| 槽位映射页签是空的，且是原生模块的表 | 需要在代码里声明数据集 |
| 后台日志有「求不出条件」但槽位确认配了 | 规则参数或条件树有问题 |
| 改了配置等了很久还不生效 | 缓存或部署问题 |

## 给开发的排查线索

（管理员不用看，反馈问题时可以把这段一起发给开发）

- 权限清单来源：`GrantDecisionService#listAllowedPermissions`，缓存 key
  `grant_user_permissions:<租户>:<用户>`，TTL 30s
- 菜单树来源：`listAllowedMenuIds`，同源判定 + 按 `system_menu` 父链补全祖先
- 单点判定：`GrantDecisionService#hasPermission`，一个权限串对应多行资源时逐行建链、
  任意一行通过即通过
- 字段模式：`GrantDecisionEngine#resolveFieldMode`，三层合并取最严格
- 行过滤：`DataRowFilterResolver#resolve`，求不出条件时贡献 `1=0` 或整表 denyAll
- 实例可见性：`BpmInstanceParticipantServiceImpl#isParticipant`
