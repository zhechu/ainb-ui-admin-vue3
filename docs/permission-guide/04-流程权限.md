# 04 · 流程权限

流程的权限比普通表单多一层：除了「能不能发起/管理」，还有「**这张单子他能不能看**」。
这两件事判据完全不同，分开讲。

---

## 一、流程级权限：谁能发起、谁能管

**入口**：【工作流程 → 流程模型】→ 找到流程 → 进它的定义列表 → 「权限配置」

> 这个页面是从流程模型列表跳进去的（地址形如 `/bpm/manager/definition?key=流程标识`），
> 侧边栏里没有单独的菜单项。

### 四个动作

| 动作 | 含义 | 谁该有 |
|---|---|---|
| `START` | 能发起这个流程 | 业务经办人 |
| `DESIGN` | 能改这个流程的设计 | 流程管理员 / 实施 |
| `MANAGE` | 流程管理员，能看它的**全部**实例、能强制取消 | 流程负责人 |
| `VIEW_ALL` | 能看它的全部实例，但不能管 | 审计、监控岗 |

**四个动作必须分开配，`VIEW` 不能替代它们。** 用 `VIEW` 一把抓的话，
「能看到这个流程」就等于「能发起、能改设计」，等于没区分。

### 分类继承

流程挂在**流程分类**下，分类也是资源。给分类配授权，它下面所有流程都继承。

典型用法：给「人事类流程」这个分类配 `START` 放行给全体员工，
个别敏感流程（如「薪资调整」）再单独配 DENY。

> ⚠️ 分类上的 DENY 会拦住整个分类。只想拦一个流程就配在那个流程上。

### 发起范围那三个字段

流程设计里有「可发起人 / 可发起部门 / 流程管理员」三个配置。它们**不是独立的权限来源**——
每次部署流程时，系统会把它们**投影成 `sys_grant` 授权**（`START` / `MANAGE`）。

这意味着：

- 你在流程设计里配发起范围，和在权限配置里配 `START`，最终落到同一张表
- **留空表示「谁都能发」**，会被投影成一条 `ALL:all-users` 的显式授权
- 判定只看 `sys_grant`，不再回头读那三个字段

> 🔴 **绕过部署接口改流程定义会出事**。投影只在部署钩子里跑。
> 如果从别的环境导入流程定义表、或者直接 UPDATE 那三个列，投影不会跑，
> 而判定处已经不看旧字段了 —— 结果是**那些流程谁都发不了**。
> 补救办法是重新部署一次流程，或者请开发跑一次投影脚本。

## 二、实例级可见性：这张单子他能不能看

和上面完全是两回事。一个人可能有 `START` 权限（能发起请假），
但看不到别人发起的请假单。

### 判定顺序

```
1. 他是这条实例的参与人吗？        → 能看
2. 他是这个流程的管理员（MANAGE）？ → 能看
3. 他有这个流程的 VIEW_ALL？       → 能看
4. 否则                            → 看不到
```

### 什么算「参与人」

系统在六个时机自动登记参与人，存在参与表里：

| 参与类型 | 什么时候登记 | 可写 |
|---|---|---|
| 发起人 | 发起时 | 否 |
| 审批人 | 任务分派给他时 | **是** |
| 转办出去的原受理人 | 他把任务转给别人时 | 否 |
| 委派出去的原受理人 | 委派时 | 是 |
| 加签发起人 | 加签时 | 是 |
| 抄送人 | 抄送时 | **否（永远只读）** |

抄送人永远只读是刻意的：抄送的语义是「知会」，不是「参与办理」。
如果把抄送人和审批人记成同一种，「抄送给财务看一眼」就变成「财务能改这张单子」。

> ⚠️ 参与记录只对新发生的流程自动登记。历史流程需要跑一次补登记脚本。
> 症状是「昨天还能打开的单子今天打不开」。

## 三、父子流程可见性

一个流程可以用子流程节点调起另一个流程。这时有三个开关，在流程设计的
「子流程可见性」里配：

| 开关 | 含义 | 默认 |
|---|---|---|
| `parentCanViewChild` | 父流程的参与人能看这条子流程 | **开** |
| `childCanViewParent` | 子流程的参与人能看父流程 | **开** |
| `childCanViewSibling` | 同一主单据下的子流程互相可见 | **关** |

### 最重要的一条规则：谁被看，谁做主

**配置取「被查看的那条实例」所属流程的配置，不是查看者那边的。**

举例：主单据 A 调起子流程 B（薪资核定）。
要让「A 的发起人看不到 B」，得在 **B（子流程）** 上关掉 `parentCanViewChild`，
配在 A 上无效。

这条口径是统一的，也是刻意选的。用查看者那边的配置也说得通，
但两边混用必然出现「同一对父子，从上往下看和从下往上看结论不一致」，
那种不一致没人能凭直觉推出来。

### 兄弟默认不可见

`childCanViewSibling` 默认关闭，开启等于让同一主单据下所有子流程互相透明。
**这一条几乎不该开。**

### 典型场景

「入职流程」调起「薪资核定」子流程：

| 想要的效果 | 怎么配 |
|---|---|
| HR 能看到薪资核定 | HR 是入职流程参与人，子流程 `parentCanViewChild` 保持开 |
| 入职申请人**看不到**薪资核定 | 在**薪资核定**上关掉 `parentCanViewChild` |
| 薪资专员能看到上游入职单 | 入职流程 `childCanViewParent` 保持开 |

⚠️ 第二条会把**所有**父流程参与人都挡住，包括 HR。
要「HR 能看、申请人不能看」，就不要用这个开关，
改成在薪资核定流程上给 HR 角色配 `VIEW_ALL`，同时 `parentCanViewChild` 关掉。

## 四、子流程调起授权

父流程调起子流程时，也要过权限——判定主体是**系统身份** `SYSTEM:bpm-engine`，
不是发起人。

默认是**放行**的（否则现存的父子编排全部跑不动）。只有配了显式 DENY 才会拦：

| 主体 | 资源 | 动作 | 效果 |
|---|---|---|---|
| SYSTEM `bpm-engine` | 子流程 | `START` | **拒绝** |

配上之后，父流程走到子流程节点时会被拦住，审批时会提示「无权调起」。

> ⚠️ 这里只看子流程**自身**的 DENY，不看它分类上的。
> 从分类继承一条「禁止调用」下来会误伤同分类的其它流程。

## 五、候选人与委托

### 候选人快照

任务分派给「发起人的部门负责人」这类动态表达式时，系统会**同时存表达式和快照**。

快照锁的是「**他当时属于哪个部门**」，不锁「那个部门现在归谁管」：

- 中途调岗 → 单子仍派给发起时那个部门（用快照）
- 部门负责人换人 → 派给**现在**在位的负责人（实时查）

第二条是刻意的：任务现在要办，就该现在在位的人办。

### 离职交接重算

离职交接重算候选人时用**当前**组织关系，不用快照——
用快照等于原样返回离职者本人，自我否定。

### 委托

委托是**晚绑定**的：任务真正到达时才解析委托关系，不是配置时就固定。
所以配了委托之后新来的任务会走委托，已经在手上的任务不动。

## 六、验证流程权限的正确方式

流程权限最容易「配了看不出效果」，因为它涉及运行时状态。建议这样验：

1. **用普通账号**（超管看不出问题）
2. 真的发起一次流程，别只看列表
3. 换一个**不相关的账号**去查那张单子的详情——应该看不到
4. 把那个账号加成参与人（比如转办任务给他），再查——应该能看到
5. 改可见性开关，重复第 3 步

第 3 步和第 4 步的对照是关键。只验「能看到」不验「看不到」，
等于没验——因为默认放行的路径太多（管理员、VIEW_ALL、全局监控权限），
很容易实际上是走了别的路放行的。
