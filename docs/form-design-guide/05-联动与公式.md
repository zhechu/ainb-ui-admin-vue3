# 05 · 联动与公式

## 公式

给字段配一个表达式，值由别的字段算出来。

```
{数量} * {单价}
SUM({明细.金额})
```

- 支持四则运算、比较、常用函数与聚合函数
- **结果由服务端权威重算**：前端算的只是即时显示，落库前服务端会用自己的结果覆盖

### 为什么服务端要重算

前端提交的推导值不可信 —— 用户可能开着一个旧版本页面，也可能直接改请求。
做法统一是「重算并覆盖」而不是「校验前端算得对不对然后报错」：
报错会让正常操作莫名失败（旧页面算出来的值本来就可能与新规则不同）。

### 子表里的公式按【行】求值

明细行里的 `{数量} * {单价}` 指的是**同一行**上的两个值，不是主表上的同名字段。
主表公式可以用聚合函数引用整张明细表：`SUM({明细.金额})`。

求值顺序是「先算明细、再算主表」—— 反过来的话主表拿到的是还没算过的明细。

## 联动规则

「当条件满足时，对某些字段做某些事」。

- **触发时机**：表单加载时 / 字段变化时
- **条件**：字段 + 操作符 + 值，多条之间 AND / OR
- **动作**：显示 / 隐藏、必填 / 取消必填、可填 / 只读、赋值、清空

### ⚠️ 只写「满足时怎样」，不写「不满足时怎样」

这是联动规则最常见的错误。只配了 `then` 没配 `otherwise` 的话：
条件满足过一次、之后又不满足了，字段会**停在满足时的状态**。

表现是「金额填了 200，原因字段出来了；再改回 50，原因还留在那里」。

### 服务端会复校验

联动配的「不可填」「必填」，服务端在提交时会再判一遍：

- **不可填的字段带了值** → 丢弃。最常见的原因不是攻击，而是前端把整个表单对象原样提交了
- **必填的字段是空的** → 报错
- **既必填又不可填**（规则互相矛盾）→ 报错，并且会说明是规则配错了，不是用户的问题

## 脚本（过渡能力）

在表单上写一段 JS，挂在 `onLoad` / `beforeSubmit` / `afterSubmit` 上。

**⚠️ 内核的必填校验先于 `beforeSubmit`。** 必填没填时脚本根本不会执行 ——
想「在 beforeSubmit 里补一个必填提示」的写法永远不会触发。

打开表单时的顺序是：填相对日期默认值 → 回填数据 → 金额大写 → 联动 `LOAD` → 脚本 `onLoad`。
脚本排在联动之后，否则它刚设好的显隐会被紧接着跑的联动覆盖掉。

## 这些配法会静默失效

| 配法 | 表现 |
|---|---|
| 联动只配 then 不配 otherwise | 条件不再满足时字段停在原状态 |
| 公式引用了不存在的字段 | 发布校验会拦。**若绕过发布直接改配置**，公式恒定算出空值且不报错 |
| 公式之间循环引用 | 发布校验会拦 |
| 子表公式引用主表字段 | 作用域不同，取不到值 |
| 在 beforeSubmit 里做必填提示 | 内核必填先跑，脚本根本不会执行 |
