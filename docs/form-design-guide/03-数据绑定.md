# 03 · 数据绑定

把表单字段接到物理表上。这一步配错的后果通常是「提交成功但数据不对」，比报错难查。

## 主表

- **主表名 / 主键列**
- **主键策略**：
  - *雪花* —— 推荐。导出导入到别的环境时号不变
  - *自增* —— 由数据库生成

## 字段映射

每个表单字段 → 一个物理列，并声明该列的 JDBC 类型。类型用于：
写入时的值转换、发布校验时的列型兼容检查、列表查询时的条件构造。

## 审计列自动填充

四个列（创建人 / 创建时间 / 更新人 / 更新时间），每个有三种模式：

| 模式 | 含义 |
|---|---|
| 系统自动填充 | 后端写。**推荐** |
| 手工维护 | 当成普通表单字段，由用户填 |
| 不启用 | 两边都不写 |

**⚠️ 表里没有这些列时必须选「不启用」**，否则后端会往不存在的列写值，提交直接失败。

## 逻辑删除

勾上后，删除变成「把标记列改掉」，查询自动带上「未删除」条件。

配三样：列名、删除值、正常值，以及值类型（数字 / 字符串）。
`bit(1)` 列用数字类型、删除值 `1`、正常值 `0`。

## 乐观并发锁

勾上后，更新时带上版本号，版本对不上就拒绝并提示「数据已被他人修改」。

**不开的后果**：两个人同时打开同一条记录，各改各的字段，后提交的把先提交的整片覆盖掉，
而且**双方都以为自己存成功了**。

**⚠️ 版本列不能同时被表单字段映射。** 它由后端维护，映射成表单字段会让两边抢着写，
发布校验会拦住这种配法。

## 子表（一对多）

一个子表配置对应一个子表控件：

- **子表名 / 外键列 / 子表主键 / 主键策略**
- **字段映射**：子表控件内部的字段 → 子表的列
- **逻辑删除**：子表自己的一份配置

提交时的行为是 **diff**：比对提交上来的明细与库里现有的明细，新增的插入、改过的更新、
少掉的删除。不是「全删再全插」——那样会让明细的主键和创建时间每次都变。

## 副表（一对一）

主记录的一部分字段存在另一张表里，靠同一个主键关联。适合「主表放高频字段、
副表放大字段（长文本、JSON）」。

## 关联表（只读带出）

配一个 JOIN，把另一张表的几列以只读方式带进列表。与「关联表单」不同：
这个是**查询时连表**（实时值），关联表单是**提交时重读并存快照**。

## 变更日志

勾上后，每次更新都记一条「谁、什么时候、把哪个字段从什么改成了什么」。

**⚠️ 它依赖「字段 ID 就是物理列名」这条约定**，两者不一致时记录里的字段名会对不上。

## 这些配法会静默失效

| 配法 | 表现 |
|---|---|
| 表里没有审计列却开了自动填充 | 提交失败，报「未知列」 |
| 逻辑删除的值类型选错（字符串 vs 数字） | 删除「成功」了，但列表里那条还在 —— 查询条件与写入值对不上 |
| 不开乐观锁 | 并发修改互相覆盖，双方都以为存成功了 |
| 子表外键没配 | 明细存进去了但挂不到主记录上，下次打开是空的 |
| 同一列被两个字段映射 | 提交时报 `Column 'xxx' specified twice` |
